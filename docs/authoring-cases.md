# Как писать тест-кейсы

Кейс — это YAML. Он описывает, **что бот должен делать**, и его же ферма
исполняет. Порядок работы всегда такой: сначала изучить код, потом написать
кейс, потом прогнать.

## 1. Изучить код бота

```bash
botkit-farm study ./bots/botkit-bookingbot
```

Вывод — факты из исходников: поколение сборки, команды, подписи кнопок, тексты
ответов, обработчики нажатий. Кейс, написанный по этому выводу, не содержит
придуманных команд: такой кейс упал бы на «кнопка не найдена» и ни разу не
проверил бы бота.

## 2. Написать кейс

```yaml
id: booking-happy-path        # [a-z0-9_-], станет именем отчёта и кадра
title: Запись клиента — полный путь
source: ./bots/botkit-bookingbot
builder: legacy               # legacy | newgen | reminder или ссылка на плагин
raw: false                    # true — бот сам разбирает сырой JSON (см. ниже)
mode: polling                 # polling | webhook (см. ниже)
fixture: bookingbot           # модуль с seed(db), если нужны данные
frame: window

steps:
  - send: "/start"
    expect:
      text_contains: ["Выберите действие"]
      buttons_contains: ["📅 Записаться"]
```

Поля кейса — в [README](../README.md); схема с проверками — в
`src/botkit_farm/case/model.py`. Для бота с собственным композиционным корнем
`builder` принимает ссылку `botkit-farm.adapter:<модуль>` — контракт и
референсные сборки в [adapters/](adapters/README.md).

### Сырой режим (`raw`)

По умолчанию шаг отдаётся диспетчеру готовым объектом `Update`. С `raw: true`
тот же шаг превращается в JSON, как его присылает Telegram, и бот разбирает его
сам (`feed_raw_update` → `Update.model_validate`). Диалог не меняется, но
добавляется проверка **десериализации** — пути, которым Update приходит из
polling/webhook, и самого частого класса багов: бот полагается на поле, которого
в сыром JSON нет. Режим выключен по умолчанию; если кейс с `raw: true` падает там,
где с `false` проходит, — это проблема разбора Update у бота, а не логики.

### Режим доставки (`mode`)

По умолчанию (`mode: polling`) ферма отдаёт Update диспетчеру напрямую
(`feed_update`). С `mode: webhook` она поднимает **настоящий HTTP-сервер бота** и
шлёт в него POST с сырым JSON — как это делает Telegram. Так проверяются боты,
которые поднимаются только вебхуком (`bot.py` может содержать лишь запуск
сервера), и весь middleware-стек на этом пути. Отчёт должен получить тот же
`Turn`, что и в polling.

Точка сборки сервера берётся из кода бота: `build_webhook_app(dispatcher, bot,
secret)` (aiohttp — поколения legacy/newgen) либо `app` + `set_webhook_dispatcher`
(ASGI, например FastAPI). Если такого модуля нет, кейс падает с понятной ошибкой,
а не трейсбеком. Сервер бота слушает отдельный loopback-порт; `doctor` проверяет,
что он свободен.

### Виды действия шага

Шаг делает **ровно одно** из перечисленного (несколько сразу — ошибка валидации):

| Поле | Что делает | Когда применять |
|---|---|---|
| `send:` | пишет текст клиента | команды, ввод данных |
| `click:` | жмёт кнопку **по подписи** | когда подпись известна и стабильна |
| `pick:` | жмёт кнопку **по позиции** (`first`/`last`/`0`) | даты, слоты, id — то, что клиент заранее не знает |
| `callback:` | шлёт **сырые** `callback_data`: кнопки с такими данными у бота не было | только проверка отказа на подделку (IDOR); кейс обязан иметь тег `security` или `edge` |
| `choice:` | выполняет **первое доступное** действие из списка | состояние бота не допускает одного сценария |

`pick` существует не для удобства: зашивать в кейс дату `2026-10-12` нельзя —
завтра она другая, и кейс упал бы не из-за кода бота.

`callback` — единственное действие, которое имитирует не клиента, а **атаку**:
нажатие на кнопку, которую бот никогда не показывал. `click` такого не умеет —
он жмёт только предложенное, и потому не видит подделку, а дыра в авторизации
живёт именно там, где клиент посылает несуществующие данные. Поэтому шаг
разрешён только в кейсах с тегом `security` или `edge` и только на отказ
(`silent:` или `text_contains` с отказом) — обычный путь он проверять не должен.

```yaml
tags: [security]
steps:
- callback: order_cancel   # сырые callback_data, которых бот не предлагал
  as: guest
  expect:
    silent: true           # гард промолчал; без гарда бот ответил бы
```

### Что можно ожидать (`expect`)

| Поле | Проверяет |
|---|---|
| `text_contains` | в ответе есть подстрока |
| `text_equals` | ответ в точности такой |
| `buttons_contains` | среди кнопок есть такая подпись |
| `buttons_count` | ровно столько кнопок |
| `max_len` | ответ не длиннее N (ловит цикл печати) |
| `silent: true` | бот **не** ответил |

Пустой `expect` — ошибка валидации. Кейс без ожиданий не может упасть, а значит,
не доказывает ничего.

### Повтор шага (`repeat`)

`repeat: N` выполняет шаг N раз. Внутри действия и ожидания доступны `i` (номер
повтора с нуля) и `n` (всего повторов) — это шаблон:

```yaml
- send: "Товар {{ i }}"
  repeat: 3
  expect:
    text_contains: ["ок"]
```

Один шаг превращается в три планируемых, и в отчёте они различимы (`[1/3]`…).
`repeat` нужен там, где сценарий — не список из копий одного и того же, а цикл:
корзина из нескольких товаров, постраничный вывод. `repeat` не дешевле копипасты
по количеству строк, но у него одно место правки вместо N.

### Ветвление (`choice`)

`choice:` — список действий, из которых выполняется **первое доступное сейчас**:

```yaml
- choice:
    - click: "✅ Закрыть"        # если кнопка есть в прошлом ответе
    - send: "Открыть тикет"      # запасной путь
  expect:
    text_contains: ["Тикет закрыт"]
```

`send` доступен всегда, `click` — если такая кнопка есть среди предложенных,
`pick` — если у прошлого ответа есть кнопка на нужной позиции. Если не доступно
ни одно действие, шаг даёт «кнопка не найдена», а не падает. Так описывают ботов,
у которых один и тот же шаг выглядит по-разному в зависимости от состояния
(закрыть можно только открытый тикет).

### Шаблоны (`{{ … }}`)

`send`/`click`/`pick` и строки `expect` понимают Jinja2 — **в песочнице и по
белому списку переменных**:

| Где | Доступные переменные |
|---|---|
| действие (`send`/`click`/`pick`) | `i`, `n` — индекс и число повторов |
| ожидание (`expect`) | `i`, `n`, `turns` — тексты прошлых ответов бота |

Действие рендерится **до** прогона, поэтому прошлых ответов в нём ещё нет —
`turns` там запрещён. Ожидание рендерится после, когда ответы известны:
`text_contains: ["{{ turns[-1] }}"]` сверяет с последним ответом.

Неизвестная переменная — отказ **на чтении кейса**, с её именем:

```
cases/x.yaml: шаг 1 expect.text_contains[1]: неизвестные переменные ['секрет'];
допускаются ['i', 'n', 'turns']
```

Шаблон **не исполняет произвольный код**: `{{ ''.__class__ }}` отвергается и
разбором дерева, и песочницей. Рендер живёт в процессе фермы, а не бота: в
окружении бота Jinja2 нет и быть не должно.

## 3. Прогнать

```bash
botkit-farm run cases/bots/booking-happy-path.yaml
```

**Прогон своих правок — `--local`.** Кейс указывает `source:` git-URL, и ферма
клонирует его — то есть обычный `run` проверяет удалённый репозиторий, а не
рабочее дерево. Флаг `--local` заменяет URL на существующий чекаут `bots/<bot>`:

```bash
botkit-farm run --local cases/store-checkout-creates-order.yaml
```

Чекаута нет — кейс падает с понятным сообщением. Молчаливый откат на клон был бы
хуже: он показывает зелёный прогон по коду, которого разработчик не менял.
Локальный `source: ./bots/botkit-store` флаг не трогает — он уже локальный.

## 4. Прочитать отчёт

`reports/<id>.md` — что сошлось, что нет, полный диалог и ссылка на кадр.
Если ожидание не совпало, отчёт прямо называет: что ожидалось, что пришло,
на каком шаге и что делать.

`reports/frames/<id>-fail.png` — кадр упавшего кейса (суффикс `-fail`, чтобы
не спутать с годным).

## Правила, которые нельзя нарушать

- **Подписи кнопок — те, что видит клиент.** Не callback_data: кейс проверяет
  интерфейс, а не внутреннее состояние FSM.
- **Ни одного выдуманного идентификатора.** Даты и id — через `pick`.
- **Данные фикстуры — вымышленные.** Ни настоящих имён, телефонов, адресов:
  кадры публикуются.
- **Кейс пишется по коду.** Если поведение бота изменилось, кейс честно падает —
  это цель, а не неудобство.
- **`pause` там, где троттлинг.** Иначе «бот молчит» — артефакт стенда.

## Регрессы

Поле `covers: issue-12` связывает кейс с багом. Когда баг закрыт, кейс остаётся
и следит за тем, чтобы он не вернулся.

## Покрытие ботов кейсами

Регресс в `covers` говорит, что кейс нужен. `cases/coverage.json` говорит
другое: **у каждого бота есть кейс на ключевой поток** — работа, а не только
отказ. Бот, покрытый одним админ-гейтом, доказывает, что умеет молчать гостю,
и ничего — что умеет работать. Так `support` жил с единственным кейсом
`support-admin-guard`; гейт этого не видел, потому что «кейсы есть» и «потоки
покрыты» — разные утверждения.

```bash
botkit-farm coverage            # список обязательств и проблемы
botkit-farm coverage --check    # шаг CI: падение при непокрытом потоке
```

Обязательство — `{bot, flow, case, kind}`, где `kind`:

- `positive` — кейс проверяет **работу**: клиент получает ответ;
- `gate` — кейс проверяет **отказ**: неполномочного не пускают — либо
  молчанием, либо отказом тостом на подделку `callback_data`.

Вид определяется поведением кейса, а не заголовком: gate — тот, где есть шаг с
`silent: true` **или** шаг с сырым `callback` (гард отвечает тостом
«⛔ Доступ запрещён.» — отказ виден текстом, молчания нет; определение «только
silent» отвергло бы такие кейсы как не-gate и вынудило бы объявить их
positive). У бота обязан быть хотя бы один `positive`.

## Каталог регрессов

Готовые регрессы против публичных ботов живут в `examples/`, а их список — в
манифесте `examples/catalog.json`. Каталог существует отдельно от `cases/`,
потому что у него другой контракт: `cases/` — ваши рабочие кейсы, `examples/` —
обещание «этих регрессов не станет меньше».

Каждая запись манифеста называет кейс и причину (`why`) — покрываемый путь или
дефект, к которому регресс привязан. Запись без причины отвергается схемой:
регресс, о котором не помнят, зачем он, удаляют первым.

```bash
botkit-farm catalog                 # перечислить каталог
botkit-farm catalog --check examples  # упасть, если манифест и файлы разошлись
```

Проверка смотрит в обе стороны. Если кейс из манифеста пропал — «кейс регресса
пропал». Если в каталоге появился YAML, которого нет в манифесте — «кейс не в
каталоге». Оба разрыва роняют CI, поэтому удаление регресса не проходит молча.
Манифест — JSON, а не YAML: загрузчик кейсов обходит `*.y*ml`, и YAML-манифест
был бы прочитан как битый кейс.
