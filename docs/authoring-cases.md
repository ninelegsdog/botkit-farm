# Как писать тест-кейсы

Кейс — это YAML. Он описывает, **что бот должен делать**, и его же ферма
исполняет. Порядок работы всегда такой: сначала изучить код, потом написать
кейс, потом прогнать.

## 1. Изучить код бота

```bash
botkit-farm study ./bots/botkit-bookingbot
```

Вывод — факты из исходников: поколение сборки, команды, подписи кнопок, тексты
ответов, обработчики нажатий. Кейс, написанный по этому выводу, не содержит
придуманных команд: такой кейс упал бы на «кнопка не найдена» и ни разу не
проверил бы бота.

## 2. Написать кейс

```yaml
id: booking-happy-path        # [a-z0-9_-], станет именем отчёта и кадра
title: Запись клиента — полный путь
source: ./bots/botkit-bookingbot
builder: legacy               # legacy | newgen | reminder или ссылка на плагин
fixture: bookingbot           # модуль с seed(db), если нужны данные
frame: window

steps:
  - send: "/start"
    expect:
      text_contains: ["Выберите действие"]
      buttons_contains: ["📅 Записаться"]
```

Поля кейса — в [README](../README.md); схема с проверками — в
`src/botkit_farm/case/model.py`. Для бота с собственным композиционным корнем
`builder` принимает ссылку `botkit-farm.adapter:<модуль>` — контракт и
референсные сборки в [adapters/](adapters/README.md).

### Три вида шага

| Поле | Что делает | Когда применять |
|---|---|---|
| `send:` | пишет текст клиента | команды, ввод данных |
| `click:` | жмёт кнопку **по подписи** | когда подпись известна и стабильна |
| `pick:` | жмёт кнопку **по позиции** (`first`/`last`/`0`) | даты, слоты, id — то, что клиент заранее не знает |

`pick` существует не для удобства: зашивать в кейс дату `2026-10-12` нельзя —
завтра она другая, и кейс упал бы не из-за кода бота.

### Что можно ожидать (`expect`)

| Поле | Проверяет |
|---|---|
| `text_contains` | в ответе есть подстрока |
| `text_equals` | ответ в точности такой |
| `buttons_contains` | среди кнопок есть такая подпись |
| `buttons_count` | ровно столько кнопок |
| `max_len` | ответ не длиннее N (ловит цикл печати) |
| `silent: true` | бот **не** ответил |

Пустой `expect` — ошибка валидации. Кейс без ожиданий не может упасть, а значит,
не доказывает ничего.

## 3. Прогнать

```bash
botkit-farm run cases/bots/booking-happy-path.yaml
```

## 4. Прочитать отчёт

`reports/<id>.md` — что сошлось, что нет, полный диалог и ссылка на кадр.
Если ожидание не совпало, отчёт прямо называет: что ожидалось, что пришло,
на каком шаге и что делать.

`reports/frames/<id>-fail.png` — кадр упавшего кейса (суффикс `-fail`, чтобы
не спутать с годным).

## Правила, которые нельзя нарушать

- **Подписи кнопок — те, что видит клиент.** Не callback_data: кейс проверяет
  интерфейс, а не внутреннее состояние FSM.
- **Ни одного выдуманного идентификатора.** Даты и id — через `pick`.
- **Данные фикстуры — вымышленные.** Ни настоящих имён, телефонов, адресов:
  кадры публикуются.
- **Кейс пишется по коду.** Если поведение бота изменилось, кейс честно падает —
  это цель, а не неудобство.
- **`pause` там, где троттлинг.** Иначе «бот молчит» — артефакт стенда.

## Регрессы

Поле `covers: issue-12` связывает кейс с багом. Когда баг закрыт, кейс остаётся
и следит за тем, чтобы он не вернулся.
